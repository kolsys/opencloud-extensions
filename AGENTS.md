# Working on this repository

Two services that run beside OpenCloud — `video-thumbnails` and
`file-activity` — plus `common`, the code they share. No patches to the
platform, no relational database.

## Layout

The repository is a go workspace of three modules; the root is not one, so
`go test ./...` from it does nothing and every target walks the modules in
turn.

```
common/           config, observability, CS3 gateway, S3, JetStream, HTTP
video-thumbnails/ cmd/, internal/{config,command,preview,worker,resync,importer,…}, web-app/
file-activity/    cmd/, internal/{config,command,ingest,feed,tree,resync,restore,…}
dev/              the development stand: docker compose, configs, scripts
```

Each service has its own `go.mod` and `Dockerfile` so it can be taken out on
its own. The build context of an image is the root of the repository, because
a service is built together with `common`.

## Commands

```
make build test lint fmt tidy    binaries, tests, golangci-lint, formatting
make web                         the web app of video-thumbnails (needs node)
make images                      docker images, the web app is built inside
make up down logs                the stand in dev/
```

`make test lint` is the gate; both have to pass before a change is done.

## Rules

- **Configuration is environment only.** State lives in S3 and in the
  JetStream of the platform. The local disk holds caches and temporary files:
  losing it must break nothing.
- **Events are at-least-once**, so every handler is idempotent. `FileUploaded`
  is not the signal that a file is ready — `UploadReady` without `Failed` is.
- **Own names for own things.** Streams, consumers and subjects carry the name
  of the service (`video-thumbnails*`, `file-activity*`). The consumer groups
  of the platform are never touched.
- **Check the platform, do not remember it.** Anything about how OpenCloud
  behaves — the name of a variable, the shape of an event, a route — is read
  from its sources at the pinned version before the code relies on it. A
  change that rests on such a fact names the file it was checked against, in
  the commit message.
- The version of the platform is pinned in `dev/.env`: events and proxy routes
  are an internal API of OpenCloud and move between releases.

## Style

The code follows OpenCloud, which is where its shape comes from.

- `gofmt` and `goimports`, tabs, LF, final newline. `gofumpt` stays off.
- Imports in three groups: standard library, external, own.
- Errors: sentinel `ErrXxx` in the `errors` package of the service, text
  prefixed with the name of the service; context is added with `%w`.
- Struct tags in the order `json, yaml, mapstructure, env, desc`.
- `.golangci.yml` is the one of the platform: `enable-all` minus their
  `disable` list, and comments on exported things are required.
- **English everywhere in the code**: names, logs, errors, messages, CLI text,
  documentation.

Comments say what is not obvious and nothing else:

- one line where one line is enough, and a comment on an exported thing starts
  with its name;
- inside a function, why rather than what;
- no alternatives, doubts or plans — a constraint the code keeps is stated in
  one line (`at-least-once: handler must be idempotent`), the reasoning goes
  in the commit message;
- no history (`used to be X`), no commented out code.

## Things that bite

- The image builds with `GOWORK=off` and cross compiles for `TARGETARCH`; the
  go and node stages run on the build machine. A change to a `go.mod` has to
  keep working without the workspace.
- `video-thumbnails/internal/web/dist/` is embedded with `//go:embed all:dist`
  and must exist in a fresh checkout — that is what `.gitkeep` is for. The
  build of the web app empties the directory.
- `dev/opencloud/proxy.yaml` is generated by `dev/scripts/gen-proxy-routes.sh`
  from the sources of the platform: the proxy takes over a default route only
  through the complete `policies` block. Never edit it by hand, change the
  script or `dev/opencloud/role-mapping.yaml`.
- The web client of the platform asks for a preview only when it believes the
  file has one, which it decides from a list of mime types built into the
  server. That is why `video-thumbnails` ships a web app, and why it serves it
  itself instead of being mounted into the platform.
- A request that carries the signature of a public link is authorised with
  `HEAD`, not `PROPFIND`: the platform accepts a link signature on `GET` and
  `HEAD` only.
- `THUMBNAILS_MAX_CONCURRENT_REQUESTS` of the platform counts every preview
  request, cache hits included, and answers 429 at once instead of queueing.
  It stays unset; `video-thumbnails` bounds the generations with a gate on
  the previews it passes on.
